# 监控指标

本文档整理 DataAgent 当前暴露的全部 Prometheus 指标、Grafana 看板面板与告警规则，并说明关键口径。

## 1. 采集链路

```
FastAPI 后端 (prometheus_client)
      │  GET /metrics            ← 指标唯一出口
      ▼
Prometheus  (job=dataagent-backend, scrape_interval=15s)
      ├─▶ Grafana 看板「DataAgent · Agent 运行总览」
      └─▶ Alert Rules (evaluation_interval=15s)
                └─▶ Alertmanager ──▶ alert-sink / 飞书 webhook
```

| 组件 | 配置 |
|---|---|
| 指标出口 | 后端 `/metrics`（`prometheus_client` 默认 registry） |
| 抓取任务 | 仅一个：`job=dataagent-backend`，`metrics_path=/metrics`（job 即服务标识，不再额外加 `service` 标签）；`instance` 由 relabel 丢弃，避免本地/容器切换或换端口后同一模型产生两条序列 |
| 抓取/评估间隔 | 均为 15s（`infra/monitoring/prometheus.yml`） |
| 指标定义 | `backend/src/codegenx/ai_service/trace/metrics.py`（唯一出口） |
| 埋点门面 | `memory/metrics.py`（记忆域，埋点失败静默，不阻断业务） |
| 告警规则 | `infra/monitoring/prometheus_alerts.yml` |
| 分组/抑制 | `infra/monitoring/alertmanager.yml` |



## 2. 指标清单

### 2.1 Session / Turn

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_sessions_total` | Counter | — | 会话建立总数（全局累计，不分 app/状态） |
| `codegenx_active_sessions` | Gauge | — | 当前运行中的会话数（全局单值，直接看当前值） |
| `codegenx_turns_total` | Counter | `app_id`, `status` | 轮次总数（按结束状态） |
| `codegenx_turn_duration_seconds` | Histogram | `app_id` | 单轮耗时（1s~300s 分桶） |

> 会话时长不采集：会话由空闲超时关闭，时长被超时主导，无排障价值。

Grafana 面板：

| 面板 | 类型 | 查询 | 回答的问题 |
|---|---|---|---|
| 活跃会话 | Stat | `codegenx_active_sessions`（单位后缀 `/ 100`，上限暂硬编码 100） | 会话池水位（快满没有） |

### 2.2 LLM 调用

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_llm_calls_total` | Counter | `app_id`, `model`, `trigger`, `outcome` | 每次实际调用尝试。`trigger`=触发来源（agent 名或后台组件名），`outcome`=`ok` 或 `error_{retryable\|context_overflow\|fatal\|logic}` |
| `codegenx_llm_latency_seconds` | Histogram | `model` | 调用往返延迟（含流式收口），0.5s~120s |
| `codegenx_llm_first_token_seconds` | Histogram | `model` | 首 Token 延迟，0.1s~10s |
| `codegenx_llm_prompt_tokens_total` | Counter | `app_id`, `model` | 发送的 prompt tokens |
| `codegenx_llm_completion_tokens_total` | Counter | `app_id`, `model` | 接收的 completion tokens |
| `codegenx_llm_last_call_latency_seconds` | Gauge | `model` | 最近一次调用延迟（供单次超时告警） |

口径说明：

- **只统计成功调用的延迟/首 Token**，失败尝试只进 `calls_total`，避免慢失败污染 P95。
- **token 计数只有一处喂入**（韧性层 `_record_usage`），`app_id` 按上下文归因，避免同一次调用重复计数。
- 每次 attempt 喂一次 `calls_total`，重试各算一次。

Grafana 面板：

| 面板 | 类型 | 查询 | 回答的问题 |
|---|---|---|---|
| 模型请求速率 | Time series | `sum by (model) (rate(codegenx_llm_calls_total{outcome="ok"}[1h]))` | 流量是否掉量（掉量=已切 fallback） |
| 模型错误率（5m 窗口） | Time series | `rate(calls_total{outcome=~"error_.*"}[5m]) / rate(calls_total[5m])` | 错误率趋势（>20% 触发告警） |
| LLM / Embedding 延迟 P50/P95 | Time series | `histogram_quantile(0.5\|0.95, rate(llm_latency_seconds_bucket[1h]))`，P95 用 `or` 合并 embedding | P95 爬升=慢劣化 |
| 首 Token 延迟 P50/P95 | Time series | `histogram_quantile(0.5\|0.95, rate(llm_first_token_seconds_bucket[1h]))` | 用户感知的首字响应 |
| 生成速率 | Time series | `rate(completion_tokens_total[1h]) / rate(llm_latency_seconds_sum[1h])` | tokens/s |

### 2.3 LLM 韧性（重试 / 降级 / 熔断 —— 全部"当前状态"口径）

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_llm_retrying` | Gauge | `model` | 此刻有几个调用正在退避重试中（进入退避 +1，醒来 -1） |
| `codegenx_llm_last_retries` | Gauge | `model` | 最近一次调用实际重试了几次（0 = 一次成功） |
| `codegenx_llm_last_fallback_seconds` | Gauge | `model`, `target` | 最近一次降级切换：`model`=主模型，`target`=实际降级到的模型，值=切换时刻 unix 时间戳 |
| `codegenx_llm_last_failure_seconds` | Gauge | `model`, `outcome` | 最近一次失败尝试的时刻（`outcome`=错误分类），结合熔断状态判断是否恢复 |
| `codegenx_llm_last_failure_info` | Gauge | `model`, `error_class`, `trace_id` | 最近一次失败的 `trace_id` 与分类（值恒 1）；每模型只保留一条，换 trace 时移除旧序列 |
| `codegenx_llm_circuit_state` | Gauge | `circuit` | 熔断状态：`0`=CLOSED，`1`=HALF_OPEN，`2`=OPEN |

口径说明：

- 韧性域**不保留历史累积**（重试总数/降级总数/熔断打开总数已删除）：运维关心的是"现在在不在挣扎、降没降级、什么时候失败的"，不是累计次数。
- **用户主动停止/任务取消不计失败**：`CancelledError` 不记录、不重试；停止时异步生成器收尾若发生跨 Context 复位异常，已由 span/context 层吞掉，不会误记成 `error_logic`。
- 只有 `RETRYABLE` 类失败累计熔断计数；`FATAL`（401/404）与 `CONTEXT_OVERFLOW` 不计入，避免配置错误把模型永久打死。
- 状态 Gauge 进程启动即上报，无流量也能看到 `CLOSED` 行。

Grafana 面板：

| 面板 | 类型 | 查询 | 回答的问题 |
|---|---|---|---|
| LLM 熔断 OPEN 数 | Stat | `count(count by (circuit) (codegenx_llm_circuit_state == 2)) or vector(0)` | 此刻有几个模型不可用 |
| LLM 熔断状态时间线 | State timeline | `max by (circuit) (codegenx_llm_circuit_state)`（`circuit` 即图例） | 断态持续多久、何时恢复 |
| 模型健康矩阵（LLM + Embedding） | Table | 见下表，主源为 `llm_*` / `embedding_*` 韧性 Gauge | 每个模型当前状态全貌（病因与影响面） |

模型健康矩阵列含义：

| 列 | 来源 | 说明 |
|---|---|---|
| 模型 / 熔断键 | `llm_circuit_state or embedding_circuit_state` | LLM 与 Embedding 合并展示，`circuit={provider}:{model}` 解析出模型名 |
| 熔断状态 | `*_circuit_state` | 0=CLOSED / 1=HALF_OPEN / 2=OPEN |
| 重试中 | `llm_retrying` | >0 即此刻有调用正在退避挣扎 |
| 上次重试 | `llm_last_retries` | 最近一次调用重试了几次（0=一次成功） |
| 降级至 | `llm_last_fallback_seconds` 的 `target` 标签 | 切到了哪个降级模型；embedding 无降级，恒空 |
| 最近失败 | `llm_last_failure_seconds or embedding_last_failure_seconds` | 显示确切时刻（不限窗口）；对照熔断状态判断是否恢复。**用户主动停止不算失败** |
| 失败分类 | `llm_last_failure_info` / `embedding_last_failure_info` 的 `error_class` | `retryable`/`fatal`/`context_overflow`/`logic`（embedding 为 `timeout`/`rate_limit`/`auth`/`connection`/`other`） |
| trace_id | 同上两个 info 指标的 `trace_id` 标签 | 直接回 `telemetry.trace_spans` 定位这次失败的入参与异常 |

> 矩阵各列**常驻显示**：「降级至」「最近失败」「失败分类」「trace_id」在无数据时由查询侧兜底填 `-`（PromQL 用 `or 0 * 熔断状态派生行`，避免空 frame 导致整列消失）；熔断状态列带颜色渲染（CLOSED 绿 / HALF_OPEN 黄 / OPEN 红）。

> **请求量与延迟不在矩阵里**：7 天请求数已移除（调用量趋势放前端，直查 `telemetry`），P95/首 Token 已有下方独立时序图，矩阵只回答"状态 + 病因 + 去哪查"。

> 矩阵与熔断状态**不是重复信息**：熔断只回答「断没断」，矩阵回答「病因与影响面」——错误率 30% 但未达连续失败阈值时熔断不会打开、FATAL(401) 设计上不计熔断失败，这些情况只有矩阵能看见。
>
> 「最近失败」显示的是真实时间戳而非窗口计数：窗口（如 1h 错误数）过了就什么都看不到，时间戳永远能回答"上次失败是什么时候"。矩阵同时覆盖 Embedding，故其面板不重复列在 2.5。

### 2.4 工具

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_tool_latency_seconds` | Histogram | `app_id`, `tool_name` | 真实工具执行耗时，0.01s~120s。**不含 `dispatch_agent`**：它耗时=子 Agent 全流程（数十秒），会把真实工具 P95 掩盖 |
| `codegenx_tool_failure_streak` | Gauge | `tool_name` | 同一工具**跨会话连续失败**次数，任一成功清零；`>0` 即"还在错着" |
| `codegenx_tool_failure_streak_since_seconds` | Gauge | `tool_name` | 本轮连续失败的**起点**时间戳（0=无 streak）；`now-该值`=已连续失败多久 |
| `codegenx_tool_failure_last_seconds` | Gauge | `tool_name` | 本轮连续失败中**最近一次失败**的时间戳（成功清零） |
| `codegenx_tool_last_failure_info` | Gauge | `tool_name`, `trace_id`, `error_class` | 最近一次失败的 trace_id 与分类（值恒 1）；每工具只保留当前一条，换 trace/恢复成功时移除旧序列 |
| `codegenx_tool_circuit_state` | Gauge | `tool_name` | 工具/数据源熔断状态（0/1/2 同 LLM） |

失败分类口径（`error_class`）：

| 分类 | 含义 | 计入熔断 |
|---|---|---|
| `arg_invalid` | LLM 生成的参数/SQL 有问题（业务失败） | 否 |
| `subagent_failed` | `dispatch_agent` 派发的子 Agent 未产出结果（max_steps 耗尽/持续失败） | 否 |
| `execution` | 工具执行本身失败：连接、资源、驱动异常 | 是 |
| `timeout` | 超时 | 是 |

> `circuit_open`（熔断打开导致的快速失败）**计入连续失败**（该工具确实在快速失败），但不覆盖归因：`tool_last_failure_info` 仍保留导致熔断那次失败的 `trace_id` 与分类，避免看板只剩"circuit_open"看不出病因。

Grafana 面板：

| 面板 | 类型 | 查询 | 回答的问题 |
|---|---|---|---|
| 工具熔断 OPEN 数 | Stat | `count(count by (tool_name) (codegenx_tool_circuit_state == 2)) or vector(0)` | 此刻有几个工具不可用 |
| 工具熔断状态时间线 | State timeline | `max by (tool_name) (codegenx_tool_circuit_state)` | 工具可用性（何时断、多久恢复） |
| 工具延迟 P95 TOP6 | Time series | `topk(6, histogram_quantile(0.95, sum by (le, tool_name) (rate(tool_latency_seconds_bucket{tool_name!="dispatch_agent"}[6h]))))` | 最慢的真实工具；`dispatch_agent` 不入图（其耗时=子 Agent 全流程），窗口内无调用的工具会断点 |
| 工具当前连续失败 | Table | `streak > 0` + `streak_since_seconds*1000` + `failure_last_seconds*1000` + `last_failure_info` | 还在失败的工具、连败次数、起始/最近失败时间、trace_id 与分类；为空=全部正常 |

> 工具调用量/失败率**不在监控侧做**：原 `tool_calls_total` 与「工具 7d 调用量」面板已删除。每工具每日调用趋势需要"按天聚合 + 图+表"，Prometheus 不适合，改由前端「运行统计」页（`/admin/toolStats`）经 `GET /api/stats/admin/monitor/tools/daily` 与 `GET /api/stats/admin/monitor/llm/daily` 分别直查 `telemetry.tool_semantics`、`telemetry.trace_spans`（op_type='llm'，模型取 attributes.model）出表+图。

### 2.5 Embedding

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_embedding_calls_total` | Counter | `model`, `outcome` | 批次调用数（`ok`/`error`）；7d 趋势不在监控侧展示 |
| `codegenx_embedding_latency_seconds` | Histogram | `model` | 批次往返延迟（含重试），0.05s~30s |
| `codegenx_embedding_last_failure_seconds` | Gauge | `model`, `error_class` | 最近一次批次失败的时刻与分类：`timeout`/`rate_limit`/`auth`/`connection`/`other` |
| `codegenx_embedding_last_failure_info` | Gauge | `model`, `error_class`, `trace_id` | 最近一次失败的 `trace_id` 与分类（值恒 1）；每模型只保留一条 |
| `codegenx_embedding_circuit_state` | Gauge | `circuit` | Embedding 熔断状态（0/1/2） |

口径说明：

- 语义单位是**批次**，不是单次 HTTP 调用：一次 `embed_texts` 可能内含多次重试，最终收口为一条 `ok` 或 `error`。
- 因此**没有首 Token 指标**——embedding 是批量非流式接口，首 Token 无业务意义；**也没有批大小直方图**（批大小由配置固定，分布无信息量，已删除）。
- **没有 fallback 指标**——embedding 不做模型降级，只做熔断 fast-fail，由调用方降级承接（见 4.3）。
- 熔断键同样是 `{provider}:{model}`。

Grafana 面板：

| 面板 | 类型 | 查询 | 回答的问题 |
|---|---|---|---|
| Embedding 最近失败时间 | Table | `codegenx_embedding_last_failure_seconds * 1000` | 最近一次批次失败的时刻与分类 |
| （共享）LLM / Embedding 延迟 P50/P95 | Time series | 见 2.2 | Embedding P95 与 LLM 同图对比 |
| （共享）模型健康矩阵 | Table | 见 2.3 | Embedding 熔断状态/最近失败已在矩阵内 |

### 2.6 Memory

Memory 是定时任务域，**任务完成明细以数据库为真源**（PostgreSQL `memory.memory_task`：status/retry_count/last_error/produced_count/payload），指标只保留「当前状态 Gauge（可告警）」+ 少量质量趋势。触发原因、准入拒绝、归档条数等描述性明细走日志与库，不进指标。

> 迁移 pgvector 后的一致性类指标全部下线：向量与记忆行同表同事务写入，不再有「行级同步队列」与「双源对账」，`vector_pending` / `sync_staleness_seconds` / `spotcheck_miss` 三项随 Qdrant 与 `memory_sync_checkpoint` 一并删除。

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `codegenx_memory_extract_total` | Counter | `app_id`, `status` | warm_extract 任务结果（`ok`/`failed`/`dead`）——随时间看错误率，反映提炼质量 |
| `codegenx_memory_task_pending` | Gauge | — | 队列中 pending 任务数；持续积压 = 该提炼没提炼 |
| `codegenx_memory_task_running` | Gauge | — | 正在执行的任务数 |
| `codegenx_memory_task_dead` | Gauge | — | 重试耗尽（退避 1m/5m/30m，约 4 次连续失败）的任务数，失败原因查 `memory_task.last_error` |
| `codegenx_memory_hot_token_usage_ratio` | Gauge | — | hot 层注入 tokens / 预算（最近一次采样的用户） |
| `codegenx_memory_degrade_total` | Counter | `kind` | 记忆子系统降级次数：`postgres`/`redis`/`embedding`/`timeout`（罕见且关键，按 `increase[15m]` 告警） |

> `degrade_total` 的 `kind` 是**故障归因**：embedding 服务不可用记 `embedding`，数据库不可用记 `postgres`，两者不可混用，否则无法区分是模型侧还是存储侧问题。
> 提炼质量口径：该做没做看 `task_pending` 积压，做错看 `extract_total{failed}` 趋势与 `task_dead`；向量一致性不再是「需要监控的问题」——单表单事务后它不可能分叉。

Grafana 面板：无独立面板——完成明细看库（`memory.memory_task`），队列/死信两个 Gauge 直接由告警承接，不重复上板。

> 本轮精简删除的指标及去向：`memory_task.payload.cost_ms`、`extract_triggered_total`（→ 漏斗状态在 `memory_watermark` 表 + debug 日志）、`write_rejected_total`（→ 写入日志）、`task_stuck_reclaimed_total`（→ 回收后进 pending，由队列 Gauge 承接）、`consolidate_merged_total`/`archived_total`（→ 任务 `produced_count` 审计）、`hot_count`（ratio 已覆盖），以及随 pgvector 迁移下线的 `vector_pending`/`sync_staleness_seconds`/`spotcheck_miss`/`vector_sync_fail_total`/`reconcile_missing_total`/`reconcile_ghost_total`。

## 3. Grafana 看板

看板：`infra/monitoring/grafana/dashboards/dataagent-overview.json`（uid `dataagent-overview`，文件预配 30s 自动重载），共 14 个面板，设计口径为**当前状态优先**：凡是"历史累积次数"能删的都删了；调用量趋势改到前端「运行统计」页（工具 / LLM 两个 Tab，直查 `telemetry.tool_semantics` 与 `telemetry.trace_spans`）。

面板按指标域分散在各章节（§2.1~§2.6 的「Grafana 面板」表），**指标与面板同处一节，便于对照看板读数来自哪个指标**。归属索引：

| 章节 | 指标域 | 面板数 | 面板 |
|---|---|---|---|
| 2.1 | Session / Turn | 1 | 活跃会话 |
| 2.2 | LLM 调用 | 5 | 模型请求速率、模型错误率、LLM/Embedding 延迟 P50/P95、首 Token 延迟、生成速率 |
| 2.3 | LLM 韧性 | 3 | LLM 熔断 OPEN 数、LLM 熔断状态时间线、模型健康矩阵（含列含义） |
| 2.4 | 工具 | 4 | 工具熔断 OPEN 数、工具熔断状态时间线、工具延迟 P95 TOP6、工具当前连续失败（含连败时间/trace_id） |

## 4. 告警规则

规则文件：`infra/monitoring/prometheus_alerts.yml`（group `codegenx_alerts`，interval 15s）

| 告警 | 表达式要点 | for | 级别 | 含义与处置 |
|---|---|---|---|---|
| `LLMAvgLatencyHigh` | 5m 平均延迟 > 30s | 1m | warning | 上游变慢；看错误率与 P95 曲线 |
| `LLMSingleTimeout` | 最近一次调用 > 60s | 30s | warning | 单次卡死；定位模型与上游状态 |
| `ToolConsecutiveFailures` | 连续失败 ≥ 3 次 | 15s | critical | 工具/数据源不可用；查连接与沙箱 |
| `ContextThresholdBreach` | 连续超 85% 未压缩 ≥ 3 | 15s | warning | 上下文压缩器失效或配置错误 |
| `LLMCircuitOpen` | 熔断状态 == 2 | 30s | critical | 模型被摘除，确认 fallback 正在承接 |
| `LLMErrorRateHigh` | 5m 错误率 > 20% | 2m | warning | 供应商故障或 Key/配额问题 |
| `ToolCircuitOpen` | 工具熔断 == 2 | 30s | critical | 工具已 fast-fail，查数据库/沙箱 |
| `EmbeddingUnavailable` | 有失败、无成功 | 2m | critical | 向量服务完全不可用，记忆写入/语义召回降级 |
| `EmbeddingErrorRateHigh` | 5m 错误率 > 20% | 2m | warning | 看 `error_class` 区分超时/限流/鉴权 |
| `EmbeddingLatencyHigh` | P95 > 5s | 5m | warning | 向量服务性能劣化 |
| `EmbeddingCircuitOpen` | 熔断 == 2 | 30s | critical | fast-fail 中，调用方降级承接 |

Memory 任务告警（group `memory_alerts`，interval 60s；完成明细以 `memory.memory_task` 表为真源）：

| 告警 | 表达式要点 | for | 级别 | 含义与处置 |
|---|---|---|---|---|
| `MemoryTaskDead` | dead 任务 > 0 | 1m | critical | 任务重试耗尽（≈4 次连续失败）；查 `memory_task.last_error` 定位 |
| `MemoryTaskBacklog` | pending > 50 | 10m | warning | 该提炼没提炼：消费停滞或提炼模型不可用 |
| `MemoryDegrade` | `increase(degrade_total[15m]) > 0` | 1m | warning | 记忆依赖（postgres/redis/embedding）出现降级 |

> 原 `MemoryVectorSyncBacklog` / `MemoryReconcileStale` / `MemorySpotcheckMiss` 三条告警随 pgvector 迁移下线：向量与记忆同表同事务，不存在「同步滞后」与「双源分叉」这一整类故障。

> 熔断抖动（flapping）不设独立告警：OPEN 时 critical 已响，抖动会随半开探测反复通知，效果等价；原 `LLMCircuitFlapping` 随 `breaker_opens_total` 指标一并删除。

Alertmanager 行为：

- 按 `alertname` / `circuit` / `tool_name` 分组，避免同一对象刷屏
- `critical` 组 `group_wait=5s`、`repeat_interval=30m`；`warning` 默认 1h
- **critical 抑制同 job 的 warning**（`inhibit_rules`）
- 接收端 `alert-sink:9000/alert`，接飞书/企微只需改 webhook URL

## 5. 指标为空怎么看

`prometheus_client` 的 Counter / Histogram **只在首次喂入后才产生序列**，因此以下情况「查不到」是正常的：

| 现象 | 原因 |
|---|---|
| 没有 `codegenx_llm_last_fallback_seconds` / `llm_last_retries` | 从未降级、从未重试——Gauge 未喂入不产生序列（`llm_retrying` 在熔断器创建时置 0，恒有序列） |
| 没有 `codegenx_llm_last_failure_seconds` / `*_last_failure_seconds` | 从未失败（好事） |
| `codegenx_active_sessions` 为 0 | 无运行中会话 |
| 工具当前连续失败表为空 | 全部正常或从未失败 |
| 某模型无 P95 | 该窗口内无成功调用（Gauge 类熔断状态仍会显示） |
| 面板整块空白 | 指标名与后端不一致（曾因批量改名误写成 `DataAgent_*` 导致） |

## 6. 排查索引

| 现象 | 先看 |
|---|---|
| 用户反馈「回答很慢」 | LLM 延迟 P95、首 Token P95、生成速率 |
| 「一直转圈没响应」 | `LLMSingleTimeout`、`llm_last_call_latency_seconds` |
| 「突然都失败了」 | 熔断 OPEN 数、矩阵「最近失败」列、错误率 |
| 「答非所问 / 忘记上下文」 | `context_breach_streak`（平均上下文面板已删除，见 §3 说明） |
| 「记忆检索不到」 | Embedding 成功率、`memory_degrade_total{kind="embedding"}`、Embedding 最近失败时间表 |
| 「SQL 工具老报错」 | 工具当前连续失败表（`arg_invalid`=LLM 入参问题，非工具故障；拿 trace_id 回前端 span 看报错原文） |
| 「工具直接快速失败」 | `tool_circuit_state`、工具当前连续失败表 |
